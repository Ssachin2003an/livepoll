# Requirements and delivery checklist

This checklist preserves the assignment's independently deliverable outcomes. “Complete” means the local outcome has evidence; it does not imply public deployment or submission readiness.

## 1. React experience and core user flow — Implemented locally; Preview user flow and responsive screenshots verified
- Keep React frontend source in `frontend/` separate from the Go backend in `backend/`; use reusable components, a consistent design system, proper loading states, frontend validation, error handling, and responsive layouts. Provide a clear product identity/navigation and a landing page with an explanatory hero, create/sign-in calls to action, and how-it-works content; support desktop, tablet and mobile.
- Provide signup, login and logout pages/actions; authenticated route protection; client validation and meaningful error messages; persistent authentication across refresh using the selected secure session mechanism; loading, success and error states.
- Dashboard lists only the authenticated user’s polls with question, status, total votes and creation date; provide actions to create, view, share and manage owned polls; display useful empty and load-error states.
- Poll creation has a question field and 2–10 answer options; add/remove options; reject blank question/options, duplicate choices, question outside 5–240 characters and options outside 1–100 characters in both frontend and backend; submit to the authenticated Go API; show the created poll and its real public URL; implement copy-link functionality and clear success/failure feedback.
- A valid public link can be opened and voted on without an account. Show question/options, one-vote status, current totals, counts/percentages for each choice, readable result bars, zero-vote state, and live connection state. Update without refresh; on connection loss show a useful state/fallback; reconnect with exponential backoff/jitter and resynchronize from a current snapshot. Never use mock votes, hardcoded counts, simulated live updates, frontend-only truth, or fabricated URLs.
- Restrict poll management to its owner; close/reopen supported polls and broadcast status changes; reject another user’s management attempts server-side. Confirm the close/reopen action before applying it.
- Design acceptance includes responsive/mobile-friendly touch controls, accessible labels and keyboard interactions, visible focus and sufficient contrast, readable vote-count/timestamp formatting, success/validation/error/offline states, and subtle/reduced-motion-aware animation. No dead buttons, broken images, placeholder pages, fake charts or nonfunctional links.

## 2. Go/Gin API, services and security — Implemented; unit/integration tests pass; independent audit pending
- Use Go with Gin for the real REST API and WebSocket server. Keep handlers thin: validate/parse requests, invoke service logic and map outcomes to HTTP responses. Maintain clear configuration, models, validation, repository/store, service, handler/middleware/route, Redis, WebSocket and server-lifecycle responsibilities; do not put business logic directly in HTTP handlers.
- Implement equivalent functionality for `POST /api/auth/signup`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`; authenticated `POST /api/polls` and `GET /api/polls`; public `GET /api/polls/:id`, `GET /api/polls/:id/results`, `POST /api/polls/:id/votes`; owner-only close/reopen routes (and optional owner-only update/delete only if implemented); public origin-checked `WS /api/ws/polls/:id`; `GET /healthz`; and `GET /readyz` that verifies MongoDB and Redis dependencies. Document request/response behavior and useful errors/status codes. Do not substitute hardcoded data for real work.
- Validate every user-controlled ID/body/question/option/email/password/status/membership/ownership server-side before accepting changes. Enforce request-size limits, sensible timeouts, structured logs that do not reveal passwords/tokens/secrets, safe consistent JSON errors, restricted CORS/exact origin checks, reasonable auth/vote rate limits, context cancellation, graceful shutdown and clean dependency closure.
- Hash passwords with bcrypt; never store or return plaintext. Normalize email and enforce a unique database constraint. Use a secure, expiring server-side session or signed expiring token; use appropriate HttpOnly/Secure/SameSite cookies and CSRF defense for cookie auth; enforce ownership on every protected operation; never trust the frontend. Apply production HTTPS cookie configuration and environment-only secrets; never expose stack traces, passwords, tokens, Mongo/Redis URLs or keys.
- Verify signup/login/logout/session restore, malformed and oversized input, wrong origin/CSRF, auth-required poll creation, owner authorization, and safe errors. No unresolved dead buttons, fake responses or mandatory unfinished features.

## 3. MongoDB persistence and voting policy — Verified against real local MongoDB/Redis integration
- Treat MongoDB as the durable source of truth. Persist users (ID, name, normalized email, bcrypt hash, created time), polls (ID, owner ID, question, stable option IDs/text, status and timestamps), accepted votes (ID, poll ID, selected option ID, secure voter identity/digest, creation time and Redis-sync state), and expiring sessions. Create a unique normalized-email index; unique `(pollId,voterId)` vote constraint; owner/creation, poll/option, pending-Redis-sync and session-expiry indexes.
- Accept only votes for an existing open poll and an option belonging to it. Enforce one vote per poll per anonymous voter identity on the server; reject duplicate/concurrent attempts without incrementing counts; reject invalid option IDs, nonexistent polls and closed polls; return clear responses and collect no unnecessary personal information. MongoDB is the acceptance/durability point; the cookie-derived voter identity is hashed before storage. Document that clearing cookies or using another browser/device creates another anonymous identity.
- Store votes durably so results and Redis counters can be reconstructed; never rely exclusively on Redis or process memory for permanent data. Do not claim a distributed Mongo/Redis transaction. Explain the accepted-vote marker/outbox and recovery/consistency trade-offs.

## 4. Redis, Pub/Sub and WebSockets — Local integration verified; multi-instance/network outage not verified
- Redis must do meaningful work: maintain active per-poll vote-count hashes and distribute poll events through Redis Pub/Sub so viewers on different Go instances receive updates. Do not use a Go in-memory map as the live-count database. Never broadcast a rejected vote or increment counts for invalid/duplicate votes.
- Apply Redis vote increments atomically/idempotently by durable vote ID. Persist accepted vote first; when Redis or Pub/Sub fails, keep the Mongo vote durable, mark realtime propagation pending, report that pending state, and retry from Mongo. Handle Redis reconnect/failure and rebuild counters from Mongo. During a cache rebuild, block concurrent counter changes, seed the Redis counter hash and replay-protection vote IDs from the same Mongo vote cursor, and ensure a pending outbox retry cannot overcount a vote already represented in the rebuild. Document no shared transaction and Pub/Sub's transient delivery behavior.
- WebSocket connections validate poll IDs and allowed origins; subscriptions expose only public poll data; send an initial current-results snapshot; relay validated Redis events; use safe single-writer/concurrent connection handling, bounded messages, heartbeat/timeouts, cancellation/cleanup and no goroutine leaks. Reconnecting clients must resynchronize from authoritative results.
- Frontend connects to the active poll, processes the snapshot/events without refresh, ignores duplicate vote event IDs, uses exponential retry with jitter, resynchronizes, shows live/reconnecting/offline status and handles temporary service failures.
